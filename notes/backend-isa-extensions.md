# 后端指令集扩展方案（记录，未实现）

来源：用户方向（本文件只是记录，**尚未实现**）。

> init 时检测一下指令集，然后单独多做一份 SSE4.2、一份 AVX2 和别的扩展指令集的替换方案，
> 哪些支持就把哪些插拔上去，从 TCC 原始的 SSE2 换成现代版本，SIMD 也是如此，
> baseline 只到 SSE2，其他由扩展补上。

## 要点

1. **baseline 保持 SSE2**（不变），**更现代的能力作为可选层插拔**
2. **init 时做一次 CPUID 检测**，得到能力位（sse4.2 / avx2 / 其它）
3. **每种扩展单独一份替换方案**（SSE4.2 一份、AVX2 一份、…）
4. **运行时按能力位选择**：支持哪层就接哪层，逐级向上
5. **TCC 原本写死的 SSE2 代码生成换成"按能力位选择"的形式**
6. **SIMD 向量化同理**：baseline 只到 SSE2，更宽的向量由扩展补上

## 落点（已勘察）

| 位置 | 说明 |
|---|---|
| `src/tcc/x86_64-gen.c` | 浮点代码生成：`gen_opf` / `g()` / `o()` 里的 `movsd`/`addsd`/`mulsd`（SSE2 基线） |
| 同上 | 指令选择分派：`gen_opi` / `gen_opf` / `load` / `store` |
| `src/tcc/tcc.h` | 需要加一个"能力位"结构（如 `s1->isa_avx2`），以及替换方案的注册点 |
| CPU 检测 | TCC 自己是否已有 CPUID 探测待查；没有就像 `nosse` 那样加一个开关与探测 |

## 与 WhaleJS JIT 的关系

我们的 JIT 生成的是 **C token 流**，最终由 TCC 编译成机器码 —— 也就是说：

- **TCC 后端的指令选择直接决定 JIT 产物质量**（与 IR 层优化独立、可叠加）
- token 里目前只有 `double` 运算，TCC 选 SSE2 的标量指令已经够用
- **真正的收益在 SIMD 向量化**：一次处理 2 个（SSE2/AVX）或 4 个（AVX2/AVX-512）double

## 建议落地顺序

1. **CPUID 检测 + 能力位结构**（`avx`/`avx2`/`fma`/`sse4_2`…），并暴露一个可覆盖的开关（便于测试回退）
2. 把 `x86_64-gen.c` 里写死的 SSE2 指令选择**抽成按能力位选择的表**（这一步不改行为，只做重构）
3. **SSE4.2 一层**：`roundsd` 之类可以替掉 libm 调用（和我们已经修掉的 `fmod`/`ToInt32` 同类问题）
4. **AVX2 一层**：`vmovsd`/`vaddsd` 是**三操作数**，能省掉一条 move —— 对标量代码也有收益
5. **SIMD 向量化**（最有价值、也最难）：需要 IR 层先能识别"数组上独立迭代的循环"。
   我们的 JIT 目前只覆盖标量数值函数，向量化应当作为**独立的后续方向**，
   不要和后端指令选择混在一起做

## 注意

- 这是 **TCC 后端**的改动，和我们一直在做的 `whale_jit.c`（IR/token 层）是**两条独立的线**
- 后端改动会影响 **所有** TCC 使用者，回归面比 JIT 层大得多，建议先做第 1、2 步（无损重构 + 检测）
