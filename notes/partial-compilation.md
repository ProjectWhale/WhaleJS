# 对象返回崩溃的根因，以及部分编译（半解释器 + 半原生）评估

## 一、对象返回崩溃：根因与修复（已提交 9b08494）

**症状**：JIT 编译的函数返回对象字面量时，间歇性访问违例（0xC0000005）。
`props_diff` 一次崩、一次出正确结果。返回数组没事。

**看起来**像返回路径（`ret_obj`）的问题，所以上一轮把它整段禁用了。

**实际根因在帧的尺寸上**：

`JS_CallInternal` 用 `b->whale_needs_obj` 算两件事——`whale_obj_n`（给对象槽留几个
JSValue），以及由它决定的 `alloca_size` 和 `obj_slots` 的落点。

而这个值是在 `whale_on_call(ctx, b)` **之前**读的。可 `whale_on_call` 恰恰就是
**那个会编译这个函数的调用**，编译才会设置 `whale_needs_obj`。于是：

1. 第 100 次调用到热点阈值 → `whale_needs_obj` 还是 0 → `alloca_size` 只覆盖
   `arg_count + var_count + stack_size`，**没有 8 个对象槽**
2. 同一次调用里 `whale_on_call` 编译成功，设 `whale_needs_obj = 1`
3. 同一次调用继续走 JIT 分支，跑刚生成的代码
4. 生成的代码 `JS_WhaleObjNew(ctx, 0)` 把对象写进 `obj_slots`，而它在 alloca
   **之外**（`obj_slots = stack_buf + stack_size`）
5. 8 个 JSValue（128 字节）写进 `JS_CallInternal` 自己的局部变量区（`pc`/`sp`/`sf`…）

**所以崩溃与"返回路径"无关，是那一次调用的帧小了。**

**为什么看起来和代码形状有关**：`{a:v}` 的 `stack_size` 是 2，`{a:1*2}` 是 3。
多出来的 16 字节让 `obj_slots` 落在**不同的局部变量**上；`{a:v}` 多数时候落在无害的
位置，`{a:1*2}` 踩到 `pc`/`sp`。

**为什么只在阈值那一次崩**：第 101 次调用时 `whale_needs_obj` 已经是 1，帧尺寸正确。
所以它看起来"偶发"，其实只在**第一次 JIT 执行**那一趟。

**修法**：`whale_on_call` 返回 int（1 = 刚编译），调用者据此让**这一次调用走解释器**，
下一次调用（帧尺寸正确）才第一次跑原生代码。

**顺带修的一个真实缺陷**：JIT 执行期间 `sf->cur_sp` 推到 `obj_slots + WHALE_OBJ_SLOTS`，
GC 因此会扫 `arg_buf .. cur_sp` 的**整段**，其中包含 JS 操作数栈。JIT 从不使用操作数栈，
它的内容是上一任使用者留下的垃圾——一个 tag 恰好是 "object" 的假 JSValue 就是 GC 会去
跟随的指针。现在那段被清成 `JS_UNDEFINED`。

**结果**：`array` 从 190ms 回到 ~100ms；24 个 perftest case，0 mismatch。

**教训**：一个函数"能不能用对象槽"是**编译产物**的属性，却必须在**编译之前**决定帧的
大小。这类"顺序倒置"不报错，只写出错误内存。诊断路径是打印 helper 调用 + 打印帧布局，
而不是继续盯返回路径本身。

## 二、部分编译（用户方案）评估：可行，且比上一轮的结论更好

用户方案：**不能整段原生编译的函数（带 DOM 之类外部依赖），把其中可原生编译的部分
按需要传参，编成一个独立函数再调用。**

上一轮我的结论是"外部调用不是段，是一次调用"，理由是 **QuickJS 无法从任意 pc 恢复解释**
——所以不能"跑一段原生、回到解释器、再从某处继续原生"。

用户的方案**绕开了这个限制**，而且更干净：不是"同一个函数里原生片段与解释器交错"，而是
**把可编译的区间抽成一个独立函数**，调用者（解释器）传进需要的变量、取出结果。
控制流**从不跨越边界**——片段总是执行完再返回，"从任意 pc 恢复"这个问题根本不存在。

### 已经具备的条件

- **JSValue 布局一致**：同一个 typedef（非 NaN-boxing，16 字节 `{union, int64_t}`），
  值可以直接按值传入传出，不需要格式转换。
- **"直接操作虚拟机、不走 switch"已经存在**：我们的 helper（`JS_WhaleObjNew` /
  `JS_WhaleArrSetNum` / …）就是直白的 C，读 `ctx->rt->current_stack_frame` 的帧，
  没有 dispatch 循环。用户说的"退化路径"正是这个形态。
- **生成器已经在做"把一段字节码降成 C"**：`whale_jit_gen` 现在处理整个函数体，
  改成处理一个区间是**缩小范围**，不是新机制。

### 真正的门槛

1. **区间边界必须是能独立成函数的点**。字节码的基本块边界（跳转目标、跳转之后）是
   安全边界；区间内部不能有跨边界的活值。
2. **区间内 live 的槽要变成参数/返回值**。哪些槽 live 可以从字节码算出来——生成器
   已有 `cur[]` 状态跟踪，算 live 集合是自然的延伸。
3. **边界处不能保持类型特化假设**。片段内的类型推断（`WHALE_T_*`）在边界处必须失效，
   外部可能改变变量的类型。这也是**尾片段**最容易做的原因：只有一个入口，没有后继。

### 建议的最小可行版：尾片段（tail fragment）

只处理"从某个 pc 到 return 全是数值运算"的部分：前面留在解释器（可以做 DOM 调用、
可以有任何不可编译的东西），到了那个 pc 把需要的变量传进 JIT 函数，拿到结果返回。

这正好覆盖"渲染循环末尾大量运算 + 一次 DOM 调用"这个形状——框架函数最常见的形态。

## 三、object 做成"静态偏移 + 动态查表"混合体：现在的实现就是它

用户问"动态 object 能否做成静态 struct（指针偏移）与动态查表的混合体"。

**能，而且现在的实现就是它**：

- 每个属性访问点持有一对缓存：`_ws.fs[fc]`（解析时的 shape）与 `_ws.fp[fc]`（属性值地址）
- **第一次**访问走 `JS_WhaleObjFieldPtr` 查一次（`find_own_property`）——"动态查表"
- **之后**比较 `_ws.fs[fc] != JS_WhaleObjShape(ctx, os)`，相等就直接读 `*_ws.fp[fc]`
  ——"静态偏移"
- 更强的情形：编译期能证明"这个函数执行期间形状不变"（没有 call 在循环里 + 每个
  `put_field` 的 atom 都被某个 `define_field` 覆盖过）→ `whale_shape_stable`，
  **连 shape 检查都省掉**，只剩一次指针解引用

效果：`object` 用例 404ms → 3-6ms。

### 还没做、但值得做的

**多态 inline cache**。现在每个访问点只记 **1 个** shape。框架里同一个函数会被不同形状
的对象调用（Vue 的 vnode 字段组合不固定）→ 单态 IC 会反复 miss，每次 miss 都回 helper
（等于解释器速度）。把 **2–4 个 shape 记在同一个访问点**，就能让"同一个函数处理几种
vnode 形状"落进 IC。这是下一步的自然方向。

## 四、"框架不给静态声明，得自己用代码分析"

- **形状（shape）就是运行时的类型信息**。QuickJS 每个对象带一个 `shape` 指针，记录
  "这个对象当前有哪些属性"。框架代码不写类型，但运行时对象的形状就是事实上的类型
  ——我们已经在用它做特化。
- **已经有的编译期分析（不需要任何注解）**：
  - `whale_shape_stable`：从字节码证明"执行期间形状不变"（判据见上）
  - `whale_var_ref_feeds_call`：向后扫描 12 条指令，判断闭包引用是否喂给了调用
  - `whale_is_call_op`：识别所有调用类 opcode（含 `call_constructor`）
- **缺的一环**：现在的 shape 缓存是 `_ws` 里的 per-call 状态，每次调用清零。要真正
  "学到"框架的类型，应该把 IC 提升到**函数级/全局**，让一次调用学到的形状对下一次
  仍然有效。这与上面的多态 IC 是同一件事。
