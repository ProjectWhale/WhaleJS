# 优化路线图：已知策略的评估与排序

本文把散落在 `notes/index.md`、`notes/reg-alloc-plan.md` 里的策略合并成一份，按
**收益 / 成本 / 地基现成度 / 风险** 重排，并给出每条的判据、落点和验证方式。

## 一、现状盘点（实测）

**缺口集中在两族**：

1. **"有 call 的对象函数"（23–35×）** —— 三个最慢的 case 全是这个形状。React/Vue
   的 `render`/`patch`/`createVNode` 也全是这个形状。
2. **"纯数值循环"（3–9×）** —— 已经进 JIT，但每次读都 `load`、每次写都 `store`。

**`object` 反超 7× 说明**：只要函数能进去、且假设成立，现有机制就能赢。**问题始终是
"进不去"**。

## 三、评估与排序

### 第一梯队：缺口最大、设计已清楚

**1. 尾片段编译（C2 + C3）—— 收益最大，优先做**

**它解决什么**：三个 23–35× 的 case 全是"大量数值运算 + 一次外部调用"的形状；React/Vue
的 `render` 也是。现在这种函数**整段退化成解释器**。

**为什么可行**（用户 2026-09 指出，见 `notes/partial-compilation.md`）：不是"同函数内
原生片段与解释器交错"（那需要从任意 pc 恢复解释，QuickJS 做不到），而是**把可编译区间
抽成一个独立函数**，由调用者传参调用。控制流从不跨越边界。

**设计要点**：

- **边界取基本块边界**（跳转目标、跳转之后）。区间内不能有跨边界的活值。
- **参数传递复用现有 wrapper 的形态**：`(ctx, JSValue *args, double *An, int *deopt,
  JSValue *ret_obj, void *var_refs)`。
- **对象类参数走 `obj_slots`**（GC 要看得见；C 栈上的 JSValue GC 扫不到）——这正是现有
  `object`/`array` 机制的自然延伸。
- **尾片段的优势**：只有一个入口、没有后继；"从某 pc 到 return 全是数值运算"时 live
  变量几乎都是数值，**直接拆箱成 `double` 传参，零 GC 风险**。这就是把尾片段排在
  通用区间编译之前的原因。
- **边界处类型假设必须失效**（`WHALE_T_*` 全部回落 `UNKNOWN`），否则跨边界推断会错。

**判据**：`whale_jit_gen` 现在遇到 `OP_call` 到非 self 时 `goto out`。改成
"先编译能编的前缀 / 后缀，把 `OP_call` 留在解释器"，需要引入**区间选择**。

**验证**：先在 `temp/probe/` 造一个"渲染循环 + 一次 DOM 风格调用"的最小用例，确认通路，
再跑全量确认 0 mismatch。

**预期**：`objfields`/`immutable_update`/`vnode_build` 从 23–35× 降到与 `object` 同档
（个位数 ms）。

**2. 小函数内联（A4 = D1）—— React/Vue 总闸门**

**它与 1 的关系**：1 让"有 call 的函数**能进** JIT"；内联让"跨函数的假设**成立**"（被调者
不外泄、参数类型可信）。**两个都做才能吃下框架场景**——只做 1，调用点仍然要建帧、装箱、
查 memo。

**判据（可内联的被调者）**：字节码可编译 + 无 `OP_call`（或调用链封闭）+ 体积小于阈值 +
非构造函数。判据所需的 `whale_jit_gen` 已经能给出"这个函数能不能编译"。

**成本**：中高。需要把被调者的字节码**插入调用点**，并把参数绑定到调用点推导出的类型
（而不是重新推断）。

**收益面**：清单里唯一"一条改动通吃所有框架场景"的项。

**3. 寄存器保留（B2）—— 纯数值循环的 3–9×**

**为什么它还在榜上**：`bitops` 8.7× / `ident` 7.2× / `locals` 4.1× 全是**已经进了 JIT**
的纯数值循环。它们慢在"每次读都 `load`、每次写都 `store`"。

**地基**：**用户已选定方向（照 8cc/9cc/chibicc 做轻量实现）**；`notes/reg-alloc-plan.md`
记录了**五次尝试**，第五次（`gen_op` 归一化）已经**通了**：`arith` 修好、`object` 404ms →
3-6ms 那批收益里就有它的贡献。留下来的边界很清楚（最多 pin 4 个浮点寄存器、跳过嵌套
循环、跳过有 call 的函数）。

**成本**：中。风险点在 `gv()`/`vstore()`/`gen_op` 三处的既有标志位交互（已有详细笔记）。

**验证**：`arith`/`locals`/`loop_sum`/`bitops`/`minmax`；回归重点 `fib`（有 call）与
`sieve`（对象槽）。

### 第二梯队：地基现成或需先查清

**4. 物化决策看见"被引用几次"（B7）**

`WHALE_EXPR_MAX=24` 已被实测证明接近最优（12 明显差、36 在噪声内）。真正的问题是
**物化决策是单遍的、看不见"这个值后面还会被引用几次"**——`bitops` 里 `v0 = i & 255` 被
引用 4 次，物化一次再引用 4 次远比内联 4 次便宜。

**落点**：`loop_begin`/`loop_end` **已经能把整个循环体缓冲下来**（当初就是为此建的），
在拿到完整循环体后做一遍引用计数、再决定谁物化。

**成本**：中。**风险低**（纯生成器内决定，不影响正确性）。

**5. 多态内联缓存（D6）**

现在每个访问点只记 **1 个** shape。框架里同一个函数会被不同形状的对象调用（Vue 的 vnode
字段组合不固定）→ 单态 IC 反复 miss，每次 miss 回 helper（等于解释器速度）。

**落点**：`_ws.fs[]`/`_ws.fp[]` 再加一组（2–4）。**成本低**（纯机制扩展），**收益取决于
内联做到什么程度**。

**顺带解决一个更根本的问题**：现在的 shape 缓存是 `_ws` 里的 **per-call** 状态，每次调用
清零。要真正"学到"框架的类型，得把 IC 提到**函数级/全局**。这和 PIC 是同一件事。

**6. 循环不变量外提（A2 = D5）—— 最容易摘的果子**

`loop_begin`/`loop_end` 已能把整个循环体缓冲下来（至今没用）。渲染循环里大量不变式
（`list.length`、`props.x`、常量对象），每条外提一次省一整轮。

**成本**：低（地基已在）。**风险低**。

**7. 参数类型特化（D3）—— 需先查清失败原因**

`scan(a)` 这类"数组/对象作为参数"的通用函数整函数进不了 JIT。

**两次失败的教训已记录**：① `whale_is_call_op` 漏 `call_constructor` 导致 `sieve` 的 `n`
被误判成数组参数（169→2166ms）；② 修了之后仍退化，且引入的生成代码报 `pointer
expected`（未查明）。

**做之前必须先做的事**：把"为什么第二次仍退化"查清楚——否则第三次还是白做。
`JS_WhaleArrBind` 地基保留，可直接用。

**收益**：同时解决 `array`（3.8×）和框架里绝大多数工具函数（`patch`/`diff`/`normalize`）。

### 第三梯队：依赖前面，或收益明确但小

**8. SIMD 向量化（B3）→ 再做 ISA 分级（B4）**

**按这个顺序，理由是 B4 现在无收益**：我们的 JIT 产物只有 `+ - * /`、比较、转换，
**没有 `roundsd` 一类可替换的目标**；AVX2 三操作数在 `gen_opf` 里因 `dst == src1` 而等价。
**真正能吃下 ISA 分级红利的是 SIMD 向量化**，而它需要"数组上独立迭代的循环"进 JIT ——
现在只有 `Uint8Array` 那条窄路径。

所以：**B4 的框架已经建好（`isa_bits` + CPUID/XGETBV 检测 + `WHALE_ISA` env 覆盖 +
`gen_sse_prefix`/`gen_sse_modrm`），先留着；等 B3 有了可 SIMD 化的循环再回来用。**

**9. 字符串拼接（D7）** —— `stringcat` 5×。识别拼接链、走 append-only 缓冲，而不是每步
新建字符串。**成本中，收益局限在这一族。**

**10. `Array.prototype` 方法内联（D4）/ `Object.keys`（D8）** —— 框架高频（`map`/`filter`/
`forEach`/`push`/`slice` 每帧上千次），但**依赖 A4 内联回调**。排在 A4 之后。

**11. 循环交换 / 嵌套扁平化（D10）** —— 改善 CPU 缓存，`nested2d` 4.5×。前提是数组访问
进 JIT（已有 `_ap`/`_an` 缓存 + `get_array_el` 内联）**且**参数特化（D3）做完。

### 第四梯队：高险高收益

**12. Proxy 动态补丁穿透（D2）**

Vue 3 的响应式就是 `new Proxy(target, {get, set})`，**每次属性访问都进 JS 陷阱**，那是它
的主要开销。做法：识别"单调陷阱"（`get` 只做 `track` + `Reflect.get`，`set` 只做
`trigger` + `Reflect.set`），特化成"直接访问 target + 内联 track/trigger"。

**收益最大，风险也最大**（要推断用户代码语义）。**但机制是现成的**：target 的属性访问
直接复用 `JS_WhaleObjFieldPtr` 那条路。**排在最后。**

### 不做 / 搁置

- **AOT 路径** —— 用户已确认搁置（当前优化收益已超预期）。
- **B1 窥孔 / B5 栈槽复用 / B6 分支布局对齐** —— 收益小，属于"做完上面再看"。
- **A1 循环展开 / A3 强度削弱 / A5 标量替换** —— 在寄存器保留（B2）做完之前，它们的
  收益会被"每次读写都访存"吃掉。

## 四、推荐顺序

```
1. 尾片段编译（C2/C3）        ← 补上 23–35× 的最大缺口，设计已明确
2. 小函数内联（A4/D1）        ← 与 1 互补，框架总闸门
3. 寄存器保留（B2）           ← 纯数值循环 3–9×，方向已选定、经验已有
4. 物化引用计数（B7）         ← 风险低、地基在
5. 多态 IC（D6） + IC 提到函数级
6. LICM（A2/D5）              ← 最容易摘
7. 参数类型特化（D3）         ← 先查清两次失败的原因
8. SIMD（B3） → ISA 分级（B4）
9. 字符串拼接（D7）
10. Array 方法内联（D4）/ Object.keys（D8）
11. 循环交换 + 嵌套扁平化（D10）
12. Proxy 穿透（D2）
```

**三条分支彼此独立，可以在 1–3 完成后并行**：表达式层（A）、后端层（B）、运行时层（C）。
现在最该做的是 **1**，因为它同时是用户混合编译方案的第一跳，也是"让有 call 的框架函数
不再整段退化"的唯一路径。
